# 文案并发与本地排队修复

日期：2026-10-20。范围：用户批准的本机文案 Agent 并发配置、Web 调度及本次四个受拒任务恢复；不代表生产发布验收。

## 原因与确认方案

13:38 的快速生成批次共六项。上游同调用方并发为 2、全局为 8，超额不排队；访问记录明确为四次 `429 concurrency_limit`、两次成功。旧适配器丢失并发拒绝语义，把四项转入受理不明核查。

用户确认：上游同调用方并发改为 6，Web 自行排队，明确并发拒绝等待重试，未知受理不得自动重提。

## 实现与运行配置

- 本机 `textAgent/api-config.local.json` 的 `max_concurrent_per_client=6`，全局上限仍为 8；原配置保存在同目录的本机备份，含秘密的文件不入库。
- Web `APP_TEXT_GENERATION_CONCURRENCY=6`；Worker 和本机启动器默认六个执行槽位。此值是部署配置，今后调整上游额度时必须同步调整，当前上游没有容量发现接口。
- 新增迁移 `0036_upstream_execution_pools`：数据库共享执行槽位及任务提交最早时间。所有 Worker 对同一文案服务源地址共享额度，不按模型或 Key 各分一套；不存储密钥。短事务领取/释放槽位，模型调用期间不持有数据库事务。
- 超额任务保持原任务、原快照和原冻结积分，进入 `QUEUED`，通过持久 outbox 调度。空位释放后继续执行；进程中断后由既有恢复机制继续。
- 仅精确的 HTTP 429 / `concurrency_limit` / 无记录 ID 响应被归为可重试拒绝，遵守 `Retry-After`。再次提交前检查每次历史尝试的未受理证据，继续使用原幂等键。其他 429、模型限流、网络异常或回执不明不套用该重试路径。
- 保存拒绝回执后中断，也能重放回执并恢复排队。未知受理的执行槽位保留至 660 秒到期，高于文案适配器最大 600 秒 HTTP 等待，避免过早腾出可能仍在上游运行的槽位。
- 历史旧适配器的 UNKNOWN 回执保持不可变。仅本轮经只读上游数据库审计、超过最长调用时限、确认对应调用方及幂等键无生成记录的四个任务，追加 `concurrency_rejection_audit` 证据后恢复；普通接口不能构造此证据。
