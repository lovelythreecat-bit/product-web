# 视频任务并发与确认恢复核验（2026-10-20）

## 实际上游能力

本次只读检查 `F:/Work/电商/videoAgent` 的 `.env` 键名、`video_agent/config.py`、`service.py`、`state.py`、`worker.py`、`worker_main.py` 和 `api_app`。没有输出访问凭据，没有更改或重启上游。

- API 端口为 8015；未发现 `.env` 中存在并发数或队列容量配置。
- `AppConfig` 没有并发数、最大排队数等字段。
- `worker_main.acquire_worker()` 使用 `worker_heartbeats.singleton_id=1` 保证单一活动 Worker；主循环依次执行 `agent.tick()`，`worker._claim()` 每次领取一条工作记录。因此当前执行器并行度为 1。
- 创建任务在同一数据库事务内写入任务、planning 工作项和幂等重放记录，立即返回 201。规划完成后等待用户确认；创建和轮询均不等于开始付费生成。
- `confirm()` 只确认指定的当前方案头，在同一事务内生成 generation、写入 queued 工作项以及幂等重放记录，返回 202。方案与生成 ID 必须保持绑定。
- 上游当前没有 API 入队容量判断，没有 `queue_full`、`overloaded` 等明确的接纳前 429 协议。上游 HTTP 错误映射也没有 429 分支。供应商侧的 429 可能作为已接纳任务内部的临时错误处理，不能转换成 Web 端安全重提依据。

未发现视频存在“只成功前两条”的硬编码限制。单 Worker 可以接受多个持久任务形成积压，但把 Web 并发设为 6 不会得到 6 路同时出片；本次建议 Web 对该视频服务使用活动工作配额 1，由共享数据库协调。扩大渲染并行度需要单独改造上游执行器，不能套用同步文本服务的设置。

## 本次适配器修复

`backend/app/agents/video.py` 原先会对已有 `confirmation_intent` 的同一请求再次 POST，依赖上游幂等记录避免再次生成。现在确认意图和 `confirmation_attempted=true` 在首次 POST 前一起持久化；已有原意图时，只能返回已经绑定的原 generation，或通过 GET 查询恢复原 generation。断线、通用 429、503 都不允许再发确认 POST。

历史数据只有 `confirmation_intent` 而没有新标记时，同样按提交结果不确定处理。新的请求键不能覆盖原意图；方案版本仍须匹配任务、当前方案头和原确认版本。创建任务通用 429 继续返回 UNKNOWN，只允许查回原任务，不能自动重新创建。

明确拒绝的业务错误由路由持久记录原命令结果；该路径与未知结果区分处理，不通过清除未知意图重新生成。

## 共享队列集成约束

共享池和命令调度由本轮主任务实现与验证。视频规划到达 `awaiting_input` / `awaiting_confirmation` 后可释放规划占用；生成只能由用户明确提交的 `MediaCommand` 触发，保留其方案版本、请求键和原任务。容量不足时保存待执行命令，取得容量后执行该原命令。轮询不得自行创建确认意图或启动生成。

如果确认 POST 已尝试而结果未知，旧的等待确认状态不是未接纳证明，不能据此重新发 POST。配额回收也必须考虑这个不确定窗口。
